# 05 - 多维表格数据模型设计

> **TL;DR**：多维表格是飞书场景的"轻量级数据库"。闭环业务的数据模型设计需要考虑**字段类型、视图配置、权限控制、索引优化**。设计得当，自动化顺畅；设计差，QPS 浪费、API 报错。

---

## 一、多维表格的本质

飞书多维表格（Bitable）是基于多维表格引擎的轻量级数据库，特点：

- **结构化**：字段类型丰富（文本、数字、日期、单选、多选、关联、公式等）。
- **可视化**：表格 + 看板 + 画册多种视图。
- **API 完整**：支持完整的 CRUD 和批量操作。
- **限制多**：每张表 ≤ 50,000 条记录，单次 API 操作有限制。

### 与关系型数据库的差异

| 维度 | 关系型数据库 | 飞书多维表格 |
|---|---|---|
| 字段类型 | 灵活（任意类型） | 预定义（文本/数字/日期/选项/关联等） |
| 表关联 | 强（外键） | 弱（关联字段，单向） |
| 公式 | 任意 SQL | 预定义公式（FIELD() 等） |
| 索引 | 自动 | 无显式索引，靠视图排序 |
| 事务 | 强 ACID | 弱（最终一致） |
| 并发 | 强（行锁） | 限制（写串行化） |
| 适用规模 | 大 | 中小（< 5 万条/表） |

**结论**：把多维表格当作"轻量级数据库"用，不要试图当 PostgreSQL 用。

---

## 二、核心字段类型

飞书多维表格支持的字段类型：

| 字段类型 | 用途 | 限制 |
|---|---|---|
| 文本（Text） | 普通文本 | 单行最长 5000 字 |
| 多行文本 | 长文本描述 | - |
| 数字（Number） | 数字 | 支持小数、百分比、货币 |
| 单选 | 状态、分类 | 最多 200 个选项 |
| 多选 | 标签 | 最多 200 个选项 |
| 日期（Date） | 日期 | 毫秒时间戳 |
| 人员 | 用户 | 自动关联通讯录 |
| 关联 | 跨表关联 | 单向，需先建表 |
| 公式 | 计算字段 | 预定义函数 |
| 创建时间 | 自动 | - |
| 修改时间 | 自动 | - |

## 五、权限设计

### 角色设计

| 角色 | 权限 |
|---|---|
| 老板 | 所有表可读，可看汇总视图 |
| 项目经理 | 项目主表全权限，客户反馈表可读，任务跟踪表可写 |
| 开发人员 | 任务跟踪表全权限（仅自己负责的），其他表只读 |
| 客服 | 客户反馈表全权限 |
| 自建应用（Bot） | 业务表写权限（通过 API 配置） |

### 协作者配置

**关键点**：通过 API 创建的多维表格**默认仅对机器人自身可见**。必须**手动添加协作者**或通过 API 添加：

```python
async def add_collaborators(
    self,
    app_token: str,
    user_open_ids: List[str],
    permission: str = "edit"
):
    """添加多维表格协作者"""
    req = CreateAppPermissionMemberRequest.builder() \
        .app_token(app_token) \
        .request_body(
            CreateAppPermissionMemberRequestBody.builder()
            .member_type("userid")
            .member_id(",".join(user_open_ids))
            .perm(permission)  # view / edit / full_access
            .build()
        ).build()
    
    resp = self.client.bitable.v1.app_permission_member.create(req)
    return resp.success()
```

## 六、性能优化

### 优化 1：避免在公式字段做复杂计算

公式字段在每次访问时计算，复杂公式会显著降低性能。

```yaml
# ❌ 不好的公式
formula: "复杂的多层嵌套 IF + 跨表关联 + 字符串处理"

# ✅ 好的公式
formula: "简单算术（加减乘除）+ 基本 IF"
```

### 优化 2：用视图而非过滤器查询

视图是预编译的查询，比临时过滤器快。

### 优化 3：批量读写

读写操作尽量**批量**（500 条/次），减少 API 调用次数。

```python
async def batch_update_progress(
    self,
    app_token: str,
    table_id: str,
    updates: List[Dict]  # [{"record_id": "rec_xxx", "fields": {...}}, ...]
):
    """批量更新进展"""
    # 分片 300 条/批
    chunk_size = 300
    for i in range(0, len(updates), chunk_size):
        chunk = updates[i:i + chunk_size]
        
        req = BatchUpdateAppTableRecordRequest.builder() \
            .app_token(app_token) \
            .table_id(table_id) \
            .request_body(
                BatchUpdateAppTableRecordRequestBody.builder()
                .records(chunk)
                .build()
            ).build()
        
        resp = self.client.bitable.v1.app_table_record.batch_update(req)
        
        if not resp.success():
            print(f"批量更新失败: {resp.code} - {resp.msg}")
        
        # 批次间延迟
        await asyncio.sleep(0.15)
```

### 优化 4：避免写并发

> 飞书官方说明：同一数据表**不支持并发调用写接口**。

如果多个进程同时写同一张表，会冲突。需要用队列串行化。

```python
import asyncio

class BitableWriteLock:
    """多维表格写锁"""
    
    def __init__(self):
        self.locks = {}  # table_id → asyncio.Lock
    
    async def acquire(self, table_id: str):
        if table_id not in self.locks:
            self.locks[table_id] = asyncio.Lock()
        return self.locks[table_id]
    
    async def with_lock(self, table_id: str, fn):
        lock = await self.acquire(table_id)
        async with lock:
            return await fn()

# 使用
write_lock = BitableWriteLock()

async def safe_update(table_id, record_id, fields):
    async def _update():
        return await self.bitable_client.update_record(...)
    
    return await write_lock.with_lock(table_id, _update)
```

## 七、数据一致性保障

### 一致性问题

自动化过程中可能出现的**数据不一致**场景：

1. 任务创建成功，但多维表格未更新 → **回写缺失**。
2. 多维表格更新成功，但任务系统未收到通知 → **同步缺失**。
3. 同一记录被多次更新，新旧值不一致 → **并发冲突**。

### 解决：定时比对

```python
async def reconcile_bitable_and_tasks(self):
    """对账：多维表格 vs 飞书任务"""
    
    # 1. 拉取多维表格所有"任务跟踪表"记录
    bitable_records = await self.bitable_client.list_all_records(
        app_token=APP_TOKEN,
        table_id=TASK_TABLE_ID
    )
    
    # 2. 对每条记录，检查对应的飞书任务
    for record in bitable_records:
        task_guid = record.fields.get("任务GUID")
        if not task_guid:
            continue
        
        try:
            task = await self.task_manager.get_task(task_guid)
        except TaskNotFoundError:
            # 飞书任务不存在，但多维表格有记录 → 删除或标记
            await self.mark_bitable_record_as_orphaned(record.record_id)
            continue
        
        # 比对状态
        bitable_status = record.fields.get("任务状态")
        feishu_status = self._map_feishu_status_to_bitable(task.status)
        
        if bitable_status != feishu_status:
            # 不一致 → 修复
            print(f"修复不一致: {task_guid} ({bitable_status} → {feishu_status})")
            await self.update_bitable_record(record.record_id, {
                "任务状态": feishu_status,
                "进展": self._get_progress(feishu_status)
            })
```

## 八、本章关键 takeaway

- 多维表格是轻量级数据库，不是 PostgreSQL，规模 < 5 万条/表。
- 闭环业务至少需要 4 张表：项目主表、客户反馈表、会议登记表、任务跟踪表。
- 字段类型要选对（文本/数字/选项/关联/公式）。
- 视图是预编译查询，性能更好。
- 协作者必须手动/通过 API 添加。
- 公式要简单，避免跨表关联复杂计算。
- 写操作必须串行化（同一表）。
- 定时对账保证最终一致性。
