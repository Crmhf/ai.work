# 02 - 三层混合架构设计

> **TL;DR**：飞书场景没有"银弹"，必须用 **API（主动）+ Automation（事件桥接）+ 定时补偿（兜底）** 三层混合架构。每一层解决不同的问题，缺一层都会让系统不可靠。

---

## 一、为什么不能只靠 API

最容易想到的方案是"全部用飞书 API"——这是错的。

原因：

### 限制 1：多维表格变更事件不开放给外部 Bot

> 飞书多维表格的变更事件**仅开放给 Automation Center**，外部 Bot（包括自建应用）无法直接订阅。

这意味着：如果你想"任务状态变了自动回写多维表格"，你**不能直接监听多维表格的变更**，必须找其他方式。

### 限制 2：API 主动轮询成本高

如果你用"每 30 秒轮询所有任务状态"的方式检测变更，假设有 1000 个任务、每天工作 8 小时，**每天调用 96,000 次**，超出 QPS 限制（任务 API 是 10 QPS）。

### 限制 3：妙记 AI 产物只能在会议后取

妙记 AI 处理会议需要时间（通常 5-30 分钟），所以你**无法实时获取**会议结论，必须设计"轮询 + 回调"机制。

---

## 二、为什么不能只靠 Automation

Automation 是飞书内置的工作流引擎，看起来能解决一切，但有限制。

### 限制 1：Automation 不能调用任意 API

Automation 的"Webhook 动作"只能配置固定 URL 和固定参数，**不能做复杂的业务逻辑**（如：根据妙记提取的内容判断应该创建几个任务、任务的负责人是谁）。

### 限制 2：Automation 可能被用户关闭

用户可能在多维表格的 Automation 设置里**误关闭**了 Webhook 规则，导致整个事件流中断。

### 限制 3：Automation 没有重试保证

Webhook 可能因为网络原因丢失，Automation **没有自动重试机制**（需要靠我们自己实现）。

---

## 三、为什么不能只靠低代码平台（Aily）

低代码平台看起来简单，但：

### 限制 1：自定义能力差

复杂业务逻辑（条件分支、循环、错误处理）实现困难。

### 限制 2：依赖平台能力边界

平台升级或下架某个能力，整个系统可能受影响。

### 限制 3：成本和用量限制

按运行次数计费，高频场景（如每日 50 场会议）成本高。

---

## 四、三层混合架构

基于以上分析，本方案采用**"API 为主 + Automation 桥接 + 定时补偿"** 的三层混合架构。

```
┌─────────────────────────────────────────────────┐
│                  第一层：API 驱动                │
│   飞书开放平台服务端 API                          │
│   - 多维表格 CRUD（10 QPS）                      │
│   - 妙记 AI 产物（5 QPS）                        │
│   - 任务 CRUD（10 QPS）                          │
│   - 会议预约（10 QPS）                           │
│                                                  │
│   特点：灵活性高，控制精确                        │
└─────────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────┐
│              第二层：Automation 桥接             │
│   飞书多维表格内置 Automation Center             │
│   - 监听记录变更事件                              │
│   - HTTP POST 到自建服务 Webhook                 │
│                                                  │
│   特点：弥补平台事件缺口                          │
└─────────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────┐
│              第三层：定时补偿                    │
│   自建定时任务（APScheduler / Cron）             │
│   - 每 5 分钟轮询                                │
│   - 比对任务系统与多维表格差异                    │
│   - 修复漏同步记录                               │
│                                                  │
│   特点：保证最终一致性                            │
└─────────────────────────────────────────────────┘
```

### 第一层：API 驱动层

**核心数据操作全部通过飞书开放平台服务端 API 完成**。

| 操作域 | 核心端点 | 频率限制 | 关键权限 |
|---|---|---|---|
| 多维表格记录 | `POST /bitable/v1/apps/:app_token/tables/:table_id/records` | 10 QPS | `bitable:app` |
| 妙记 AI 产物 | `GET /minutes/v1/minutes/:token/artifacts` | 5 QPS | `minutes:minutes:readonly` |
| 任务管理 | `POST /task/v2/tasks` | 10 QPS | `task:task:write` |
| 会议预约 | `POST /vc/v1/reserves` | 10 QPS | `vc:record:readonly` |

**API 层的优势**：
- 灵活性最强，可以做任何业务逻辑。
- 数据操作粒度细（字段级）。
- 可观测性最好（每个调用都有 trace）。

**API 层的局限**：
- 多维表格变更事件无法直接订阅。
- 妙记 AI 处理需要时间，不能实时。
- 调用频率受限（高频场景需要排队）。

### 第二层：Automation 桥接层

针对**多维表格变更事件无法被外部 Bot 直接订阅**的限制，利用飞书多维表格内置的 **Automation Center** 配置 Webhook 动作，将记录变更事件桥接到自建系统。

**工作原理**：
1. 用户在多维表格的 Automation 中配置规则："当 进展 字段变更时，调用 Webhook"。
2. Automation 监听到变更后，向我们配置的 Webhook URL 发送 HTTP POST。
3. 我们的服务收到 Webhook，调用 API 更新任务状态。

**Automation 层的优势**：
- 弥补了 API 层的事件能力缺口。
- 用户可视化配置，业务方能自助维护。

**Automation 层的局限**：
- Webhook 可能因网络原因丢失。
- 用户可能误关闭规则。
- 没有自动重试。

### 第三层：定时补偿层

**Automation 桥接虽然能覆盖大部分变更场景，但存在两个不可靠因素**：
1. Webhook 可能因网络原因丢失。
2. Automation 规则可能被用户误关闭。

因此，系统需要**定时轮询机制作为兜底**——按设定周期（如每 5 分钟）调用 API 比对多维表格与任务系统的数据状态差异，**修复漏同步的记录**。

**工作原理**：
1. 定时任务每 5 分钟触发。
2. 调用 API 拉取多维表格的最近变更记录。
3. 与任务系统的状态比对。
4. 对未同步的记录，调用 API 补偿写入。

**定时补偿层的优势**：
- **最终一致性保证**。即使前两层都失败，数据最终会同步。
- 不依赖任何外部事件机制。

**定时补偿层的局限**：
- 不是实时的（5 分钟延迟）。
- 增加了 API 调用量（需要权衡频率）。

## 五、三层如何协同

三层不是替代关系，是**互补关系**。

```
变更发生
    │
    ▼
[第二层 Automation] 准实时推送（秒级）
    │ ✓ 收到 → 完成
    │ ✗ 丢失
    ▼
[第三层 定时补偿] 5 分钟后比对修复
    │ ✓ 发现差异 → 修复
    │ ✗ 仍未发现
    ▼
[人工介入] 异常告警通知
```

### 场景 1：正常流程

- 多维表格变更 → Automation 推送 → 服务收到 → 更新任务状态 → 完成
- 整个链路秒级完成，不进入定时补偿。

### 场景 2：Automation 失败

- 多维表格变更 → Automation 推送失败（网络问题）
- 5 分钟后定时补偿检测到差异
- 调用 API 修复
- 系统告警通知运维（Automation 配置可能有误）

### 场景 3：定时补偿也失败

- 多维表格变更 → Automation 失败 → 定时补偿 API 限流
- 下一轮定时补偿继续尝试
- 累计 3 次失败 → 告警通知人工

## 六、核心数据流

```
业务数据源（多维表格）
    │
    ▼
[Meeting Scheduler] 检测阈值 → 调用 POST /vc/v1/reserves 预约会议
    │
    ▼
会议召开 → 录制 → 妙记 AI 处理
    │
    ▼
[Artifact Extractor] 轮询 GET /minutes/v1/minutes/:token/artifacts
    │
    ├── summary（纪要）
    ├── todo_list（待办清单）
    └── sections（章节）
    │
    ▼
[Task Sync Engine] 调用 POST /task/v2/tasks 创建任务
    │
    ├── 设置 origin = {meeting_id, artifact_type, ...}
    ├── 设置 assignees、due、priority
    └── 关联多维表格记录
    │
    ▼
任务执行中 → 状态变更
    │
    ▼
[Automation Webhook] 监听到任务状态变更 → POST 到我们服务
    │
    ▼
[Task Sync Engine] 调用 PATCH /bitable/v1/.../records/:record_id 更新多维表格
    │
    ▼
[Poller] 定时补偿（如有差异）
    │
    ▼
业务数据源（多维表格）更新进展
```

---

## 七、为什么是三层不是两层或四层

### 为什么不能两层

- **API + Automation**：Automation 不可靠，无法保证最终一致性。
- **API + 定时补偿**：实时性差，所有变更都延迟 5 分钟。
- **Automation + 定时补偿**：复杂业务逻辑无法实现。

### 为什么不是四层或更多

- 三层已经覆盖所有场景，再加层只是增加复杂度。
- 第四层（如消息队列）可以在特定场景下加，但不是必需。

---

## 八、本章关键 takeaway

- 飞书场景没有"银弹"，必须**三层混合**：API + Automation + 定时补偿。
- API 提供灵活性和控制力，Automation 弥补事件缺口，定时补偿保证最终一致性。
- 三层协同工作：正常走 Automation（秒级），失败走定时补偿（5 分钟），再失败升级人工。
- 核心数据流：数据 → 会议 → 妙记 → 任务 → 数据。
- **不要尝试只用 API 或只用 Automation**，实践会证明不可靠。
