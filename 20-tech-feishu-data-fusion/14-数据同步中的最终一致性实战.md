# 14 - 数据同步中的最终一致性实战

> **TL;DR**：飞书场景数据同步**无法做到强一致**，只能做到**最终一致性**。本篇讲清楚为什么、怎么做、常见问题。

---

## 一、强一致 vs 最终一致

### 强一致性（Strong Consistency）

- **定义**：写入后，**立即**所有读取都能看到最新值。
- **示例**：传统关系型数据库（PostgreSQL with ACID）。
- **代价**：性能差、可用性低（CAP 中的 C）。

### 最终一致性（Eventual Consistency）

- **定义**：写入后，**经过一段时间**，所有读取最终能看到最新值。
- **示例**：分布式系统、Cassandra、DynamoDB、飞书数据融合。
- **代价**：可能读到旧值，但**系统更可用**。

### 飞书场景的现实

- 飞书 API **不提供强一致保证**。
- 妙记 AI 处理需要 5-30 分钟。
- Automation Webhook 可能丢失。
- **只能做到最终一致**。

---

## 二、最终一致性的实现

### 三层防御

```
正常情况：
  写入 → Automation Webhook → 立即同步（秒级）

Webhook 失败：
  写入 → Automation Webhook 失败 → 定时补偿发现（5 分钟）

定时补偿失败：
  写入 → 多重失败 → 人工介入（小时级）

最终一致：
  写入 → 经过若干次尝试 → 同步成功
```

### 实现关键

#### 1. 幂等性

**同一操作执行多次，结果相同**。

```python
async def sync_with_idempotency(record_id, fields):
    """幂等同步"""
    key = f"sync:{record_id}:{hash(json.dumps(fields, sort_keys=True))}"
    
    if await redis.exists(key):
        return  # 已处理过
    
    await do_sync(record_id, fields)
    await redis.setex(key, 3600, "done")
```

#### 2. 版本号

```python
async def update_with_version(table_id, record_id, fields, expected_version):
    """乐观锁更新"""
    record = await get_record(table_id, record_id)
    if record.version != expected_version:
        raise VersionConflict()
    
    await update_record(table_id, record_id, {**fields, "version": expected_version + 1})
```

#### 3. 写队列

```python
class WriteQueue:
    """写队列：同一记录串行化"""
    
    async def enqueue(self, record_id, op):
        if record_id not in self.queues:
            self.queues[record_id] = asyncio.Queue()
            asyncio.create_task(self._process(record_id))
        
        await self.queues[record_id].put(op)
```

#### 4. 死信队列

```python
class DeadLetterQueue:
    """死信队列：失败的同步积累，等人工处理"""
    
    async def enqueue(self, record_id, fields, error):
        await self.redis.lpush("dlq", json.dumps({
            "record_id": record_id,
            "fields": fields,
            "error": str(error),
            "timestamp": datetime.utcnow().isoformat()
        }))
```

## 三、定时补偿（Reconciliation）实战

### 调度策略

```python
# 每 5 分钟：增量补偿
schedule.every(5).minutes.do(incremental_reconciliation)

# 每小时：全量对账
schedule.every().hour.do(full_reconciliation)

# 每天凌晨：清理
schedule.every().day.at("02:00").do(cleanup)
```

### 增量补偿（5 分钟）

```python
async def incremental_reconciliation():
    """增量补偿：只检查最近 10 分钟的变更"""
    since = int((datetime.now() - timedelta(minutes=10)).timestamp() * 1000)
    
    # 1. 拉取多维表格最近变更
    records = await fetch_recent_changes(since)
    
    # 2. 对账每条
    for record in records:
        await reconcile_one(record)
```

### 全量对账（每小时）

```python
async def full_reconciliation():
    """全量对账"""
    records = await fetch_all_records()
    
    diff_count = 0
    for record in records:
        if not await is_consistent(record):
            await fix_inconsistency(record)
            diff_count += 1
    
    if diff_count > 100:
        alert(f"Reconciliation found {diff_count} diffs!")
```

### 对账算法

```python
async def reconcile_one(record):
    """对账单条记录"""
    # 1. 获取对应的飞书任务状态
    task_guid = record.fields.get("任务GUID")
    if not task_guid:
        return
    
    task = await feishu.get_task(task_guid)
    
    # 2. 比对状态
    bitable_status = record.fields.get("任务状态")
    feishu_status = map_feishu_status(task.status)
    
    if bitable_status != feishu_status:
        logger.info(f"Diff: {task_guid} {bitable_status} -> {feishu_status}")
        
        # 3. 修复
        await update_record(record.record_id, {
            "任务状态": feishu_status,
            "进展": map_progress(task.status),
            "数据来源": "reconciliation"
        })
```

## 四、冲突解决策略

### 冲突类型

#### 1. 写入冲突

两个系统同时写同一记录。

**解决**：**最后写入胜出（LWW）** + 审计日志。

#### 2. 循环更新

A 写 → B 读 → B 写 → A 读 → ... 循环。

**解决**：**数据来源标记**（manual / auto_sync）+ 跳过自动触发的更新。

#### 3. 状态冲突

两边状态不一致（如一边"已完成"，一边"进行中"）。

**解决**：**优先级规则**（人工 > 自动）+ 全量对账修复。

### 优先级策略

```python
PRIORITY = {
    "manual": 100,        # 人工改动优先级最高
    "hitl_approval": 80,  # HITL 审批
    "auto_sync": 60,      # 自动同步
    "reconciliation": 40, # 对账修复
    "default": 50
}

def resolve_conflict(updates):
    """解决冲突：按优先级选最新"""
    return max(updates, key=lambda u: (PRIORITY[u.source], u.timestamp))
```

## 六、实战踩坑

### 坑 1：以为"Webhook 一定到"

**错**。Webhook 可能因网络问题、配置错误、Automation 关闭而丢失。

**正确**：**必须有定时补偿**。

### 坑 2：定时补偿频率太高

**问题**：每分钟补偿 → QPS 超限。

**解决**：
- 增量补偿（5 分钟一次）+ 全量对账（每小时）。
- 增量补偿只看"最近 N 分钟变更"。

### 坑 3：补偿逻辑写错

**问题**：补偿时使用了不同的更新逻辑，导致新数据格式错。

**解决**：**补偿逻辑必须与正常同步逻辑一致**。

### 坑 4：没有死信队列

**问题**：失败的同步一直重试，永远不成功。

**解决**：**3 次失败后进入死信队列，人工介入**。

### 坑 5：用户不知道"延迟"

**问题**：用户改了状态，立即看多维表格，发现没更新，投诉。

**解决**：**UI 上明确告知"5 分钟内同步"**，或提供"立即同步"按钮。

---

## 七、本章关键 takeaway

- 飞书场景**无法强一致**，只能**最终一致**。
- 三层防御：实时同步 → 定时补偿 → 人工介入。
- 关键机制：**幂等性、版本号、写队列、死信队列**。
- 调度策略：5 分钟增量补偿 + 每小时全量对账。
- 冲突解决：LWW + 审计日志 + 优先级规则。
- **避免 5 个坑**：以为 Webhook 一定到、补偿频率太高、补偿逻辑不一致、没有死信、用户不知延迟。
