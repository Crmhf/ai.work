# 04 - 多 Agent 协作的边界与陷阱

> **TL;DR**：协作不是越多越好。多 Agent 系统最大的陷阱是**通信爆炸、契约模糊、决策延迟**。设计不好反而比单体 Agent 更差。

---

## 一、为什么要做多 Agent

在讨论陷阱之前，先说清楚多 Agent 的价值。

**多 Agent 的本质价值**：
- **专业化分工**：每个 Agent 在自己领域做深，比"通才 Agent"在每个领域都做浅要好。
- **关注点隔离**：UI Agent 不需要懂后端，测试 Agent 不需要懂产品，减少每个 Agent 的上下文负担。
- **并行加速**：无依赖的子任务可以并发跑，缩短端到端时间。
- **错误隔离**：单个 Agent 失败不会拖垮整个系统。

这些价值是真实的，但**实现成本也很高**。多 Agent 不是"单体 Agent 数量加一"，而是**整个系统复杂度乘方级上升**。

---

## 二、三个最常见的陷阱

### 陷阱 1：通信爆炸（N×N 问题）

**症状**：Agent A 和 B 通信一次，B 又和 C 通信一次，C 又和 D 通信一次…… 通信次数按 N² 增长。

**后果**：
- Token 消耗爆炸（每次通信都要重新传上下文）
- 决策时间爆炸（每次通信都要等上一轮结果）
- 调试复杂度爆炸（每条链路都要单独追踪）

**破解方法**：
- **优先用"产物"而非"对话"通信**。A 完成工作把产物写到共享存储，B 去读，不要让 A 直接 @B 说话。
- **Ornament 设计**：所有 Agent 只和 Orchestrator 通信，Agent 之间不直接通信。这是 OpenClaw 范式的关键。

### 陷阱 2：契约模糊

**症状**：每个 Agent 都按自己理解的方式产出，最后 Orchestrator 拿到一堆格式不统一的产物，没法对齐组装。

**后果**：
- 集成时疯狂做格式转换
- Agent 之间互相"猜"对方输出
- 出错时难以定位是谁的问题

**破解方法**：
- **接口契约先于实现**：每个 Agent 的输入输出必须先用 JSON Schema / Pydantic / TypeScript Interface 严格定义。
- **示例驱动**：Orchestrator 给每个子 Agent 至少一个"输入输出示例"，比"自然语言描述"靠谱得多。
- **版本号 + 变更日志**：契约变更要发版，不能静默改。

### 陷阱 3：决策延迟与不一致

**症状**：Orchestrator 调度一轮，所有 Agent 跑完，再做一轮决策…… 整个流程跑完要十几轮对话，每轮几秒到几十秒。

**后果**：
- 用户体验差：一个"加个导出按钮"的任务要 5 分钟才能完成。
- 状态不一致：中途某个 Agent 的判断变了，前后逻辑冲突。

**破解方法**：
- **波次调度**：把不依赖的任务打包成一波，一次性并行跑完。
- **局部自治**：让子 Agent 在自己领域有"最终决策权"，不需要事事回 Orchestrator。
- **状态机而非对话机**：用显式的状态机驱动，而不是"问一轮答一轮"。

---

## 三、什么时候**不**该用多 Agent

不是所有场景都适合多 Agent。我自己的判断标准：

| 场景 | 是否适合多 Agent | 替代方案 |
|---|---|---|
| 任务能在一个上下文窗口里完成 | ❌ 不适合 | 单体 Agent + 工具 |
| 任务高度专业化、需要领域知识 | ✅ 适合 | 多 Agent + 角色分工 |
| 任务有明确的子任务边界 | ✅ 适合 | 多 Agent + 任务分解 |
| 任务需要多轮对话的开放探索 | ⚠️ 部分适合 | 单 Agent + ReAct |
| 任务响应时间要求秒级 | ❌ 不适合 | 单 Agent 或硬编码 |
| 任务质量门禁严格 | ✅ 适合 | 多 Agent + 测试 Agent |

核心原则：**能用单体 Agent 解决就别上多 Agent**。复杂度是真实的代价，不要为"架构优雅"买单。

---

## 四、多 Agent 的"最小可用架构"

如果你决定做多 Agent，建议从最小可用架构开始：

```
Orchestrator (单一决策者)
    ├── Specialist A (产物驱动)
    ├── Specialist B (产物驱动)
    └── Reviewer (统一质检)
```

- **Orchestrator 唯一**：避免多头决策。
- **Specialist 只做自己事**：不互相通信，只和 Orchestrator 通过"产物"通信。
- **Reviewer 统一质检**：避免每个 Specialist 自评（容易"自我感觉良好"）。
- **所有 Agent 共享同一个状态机**：避免状态分叉。

等这个最小架构稳定后，再根据需要扩展 Specialist 数量、加入 Memory、引入 Planning。

---

## 五、我自己的反思

我做多 Agent 项目最大的教训：

> **第一版往往过度设计**。

我曾经设计了一个 7 个 Agent 协同的复杂系统，每个 Agent 都很有"个性"，通信协议也很"优雅"。结果：
- 跑通一个简单任务要 3 分钟。
- 出错时根本不知道哪个 Agent 的哪一步出了问题。
- 改一个 Agent 的 prompt，其他 6 个 Agent 跟着受影响。

后来砍到 3 个 Agent（Orchestrator + 2 个 Specialist），反而更稳、更快、更好调试。

---

## 六、本文小结

- 多 Agent 的本质价值：专业化、隔离、并行、容错。
- 三个陷阱：通信爆炸、契约模糊、决策延迟。
- 判断标准：能用单体就不上多 Agent。
- 最小架构：Orchestrator + 2-3 个 Specialist + Reviewer。
- 第一版往往过度设计，从最小可用开始。
