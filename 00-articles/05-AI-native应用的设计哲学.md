# 05 - AI-native 应用的设计哲学

> **TL;DR**：AI-native 不是"SaaS + AI 插件"，是从头为 Agent 能力重构的产品形态。它有 5 个核心设计原则。

---

## 一、什么是 AI-native

"AI-native" 是过去一年被滥用的词。我自己的定义：

> **AI-native 应用 = 把"自主决策"当作一等公民的产品形态。它不是 SaaS 加上 AI 功能，而是从第一天起就假设"使用者可能是 Agent"**。

对比三种形态：

| 形态 | 核心假设 | 典型例子 |
|---|---|---|
| 传统 SaaS | 人操作 UI 完成一切 | Excel、Salesforce、飞书表格 |
| AI 增强 SaaS | 人操作 UI，AI 辅助 | Notion AI、飞书智能伙伴 |
| AI-native | 人或 Agent 都可以是使用者 | Cursor、Devin、Replit Agent |

注意第三种的关键差异：**使用者不一定是人**。当 Agent 是使用者时，UI 不再是必须，**API / 接口契约才是核心**。

---

## 二、5 个核心设计原则

### 原则 1：接口先于界面

传统产品设计流程：UX → UI → 业务逻辑。

AI-native 设计流程：**API 契约 → 业务逻辑 → UI（可选）**。

为什么要这样？因为：
- Agent 使用 API 调用，不需要 UI。
- UI 是给人看的，API 是给 Agent 用的，二者经常矛盾。
- 如果 API 设计好，UI 是 UI 设计师基于 API 重新包装的问题。

**实践**：
- 每个功能都有 RESTful / GraphQL API，UI 永远是"薄壳"。
- API 必须有清晰的 Schema（OpenAPI / JSON Schema / TypeScript 类型）。
- API 必须有完整的文档（不是 README，是机器可读的 spec）。

### 原则 2：可观测性先于功能

传统产品可以先做功能再补监控。

AI-native 产品**必须先有可观测性再做功能**，因为：
- Agent 行为不确定性远高于规则系统。
- 出错时你不知道是哪一步、哪个工具、哪个 prompt 出问题。
- 没有 trace 就没有 debug 能力。

**实践**：
- 每个 Agent 调用都要有 trace（输入、输出、工具调用、耗时、token）。
- 每个 trace 都要可搜索、可回放。
- 监控仪表盘比产品 UI 更早成型。

### 原则 3：可逆性先于效率

传统系统优化的是"成功的路径"。AI-native 系统必须同时考虑"失败的路径"。

为什么？因为 Agent 会犯错。**好的 AI-native 应用应该让犯错成本可接受**。

**实践**：
- Agent 做的每个写入操作都要可回滚（事务、版本控制、备份）。
- Agent 的输出默认是"建议"，需要人类确认才落地。
- 提供"撤销"按钮，比提供"加速"按钮更重要。

### 原则 4：协同先于自动化

很多 AI-native 应用的错误是"全自动"。但**真正成功的 Agent 应用是"高自动化 + 关键节点人类审批"**。

**实践**：
- 风险低的动作（查资料、写草稿）全自动。
- 风险中等的动作（修改数据库）需要预览 + 一键确认。
- 风险高的动作（删除、转账、发外部消息）必须人类审批。

### 原则 5：记忆先于推理

AI-native 应用需要**持久化记忆**，否则 Agent 每次都是"失忆状态"。

**实践**：
- 每个用户有自己的 Memory Store。
- Memory 包含：偏好、历史、上下文、关系。
- Memory 必须可被用户查看、修改、删除（隐私与可控性）。
- Memory 不是黑盒——用户能看到 Agent "记住了什么"。

## 三、一个反面教材：为什么很多 AI 工具失败

我观察到一个现象：很多 AI 工具在 demo 时惊艳，上线后崩盘。原因是**把 AI 当作"魔法"**：
- 假设 AI 不会错。
- 假设 AI 永远能理解用户意图。
- 假设 AI 不需要可观测性。
- 假设 AI 不需要回滚。

一旦上线到生产场景，这些假设全部破产：
- AI 会错，而且错得"很自信"。
- AI 经常理解错用户意图。
- 没有 trace 你根本 debug 不了。
- 错的时候想回滚？没有。

AI-native 的核心不是"AI 多强"，是"如何让 AI 出错也能让业务继续"。

## 四、给实践者的清单

如果你正在做 AI-native 应用，按这个清单自检：

- [ ] 所有功能都有 API，UI 是 API 的薄壳
- [ ] 每个 Agent 调用都有 trace，trace 可搜索
- [ ] 每个写入操作都可回滚
- [ ] 关键节点有"人类审批"开关
- [ ] 每个用户有 Memory Store，用户可查看/编辑
- [ ] 失败有兜底（fallback），不是裸跑
- [ ] 监控仪表盘比产品 UI 更早上线
- [ ] 错误率、Token 消耗、任务完成率是日常看的指标

---

## 五、我的判断

- **AI-native 是范式重构，不是功能升级**。用 SaaS 思维做 AI-native 注定失败。
- **2026-2028 是 AI-native 应用的窗口期**。再晚就只剩"传统巨头 AI 化"的红海。
- **AI-native 创业团队的最佳组成**：1 个领域专家 + 1 个 Agent 工程师 + 1 个全栈工程师。三个人就能跑出一个垂直 AI-native 应用。

---

## 六、本文小结

- AI-native = Agent 是使用者之一的产品形态。
- 5 个核心原则：接口先于界面、可观测性先于功能、可逆性先于效率、协同先于自动化、记忆先于推理。
- 失败常见原因：把 AI 当魔法，忽略工程化。
- 8 项自检清单，每个 AI-native 应用都该过一遍。
