# 06 - 个人开发者用 Agent 的实战经验

> **TL;DR**：我自己日常重度用 Agent 提效。这篇是我的真实工作流，不空谈方法论。

---

## 一、我的 Agent 工具栈

我现在每天基本不离开这几个 Agent 工具：

### 编码类
- **Cursor** —— 主力 IDE，Composer + Tab 双开。能跨文件改、跨工程搜索、跨会话记忆。
- **Claude Code（CLI）** —— 跑批处理、自动化脚本、批量重构。Cursor 不擅长的批量任务用 CLI。
- **Aider / Continue** —— 偶尔用，主要场景是 git-aware 的修改。

### 文档类
- **飞书妙记** —— 开会时全程录，结束立刻拿到纪要 + 待办。
- **Notion AI** —— 整理读书笔记、写文档大纲。
- **Claude / GPT** —— 校对、翻译、写 PRD 初稿。

### 调度类
- **OpenClaw CLI** —— 跑多 Agent 任务（项目级重构、自动化测试）。
- **Raycast AI** —— 快速调用、做临时计算。
- **Apple Intelligence** —— 系统级快捷指令。

### 数据类
- **飞书多维表格 + 妙记** —— 会议数据 → 任务数据闭环（详见 [20-tech-feishu-data-fusion](../20-tech-feishu-data-fusion/README.md)）。

## 二、我的日常工作流

### 早上 9:00-9:30：扫邮件 + 看日程

Agent 帮我做的：
- 自动汇总昨晚所有邮件，按"需回复 / 仅供参考 / 已自动处理"分类。
- 拉今日日程，标注"需要准备资料的会议"。
- 检查昨晚异步跑的 Agent 任务结果。

### 上午 9:30-12:00：深度工作（编码 / 设计）

- **编码**：Cursor 里直接用 Composer 写功能。Composer 写完我 review，不通过就让它改，改 3 次还不通过就自己写。
- **设计**：用 Claude Code 生成原型代码，跑起来看看效果，再迭代。
- **批量任务**（如批量改命名、批量加注释、批量更新依赖版本）用 CLI 跑。

**我的纪律**：Composer 不是"全自动"，是"高级协作者"。最终决定权在我。

### 中午 12:00-13:30：开会 + 复盘

- 开会时飞书妙记自动录，AI 实时生成章节。
- 会议结束的瞬间我看到结构化待办。
- 13:30 我花 10 分钟把"会议提到的待办"全部翻译成"任务"（API 调飞书任务，多维表格写一行）。

### 下午 14:00-17:30：协作 + 跟进

- 通过飞书任务看上午会议产生的任务进度。
- Agent 帮我盯多维表格里的数据变化（Automation Webhook + 我的 Python 服务）。
- 下午新需求进来，Orchestrator 拆任务，分给 3-4 个 Specialist Agent 跑。

### 晚上 20:00-21:00：异步收尾

- 早上启动的批量任务在云端跑，回来收结果。
- Agent 帮我写日报、明日 TODO。
- 个人项目（这个 ai.work 仓库）的更新也在这个时间段整理。

## 三、我观察到的 Agent 提效规律

### 规律 1：越标准化、越重复的任务，Agent 越能提效

- 写 100 个类似的接口？不擅长也变擅长了。
- 调 50 个 bug？有些 Agent 自己就能定位 + 修。
- 改 30 个文件的命名规范？一次性完成。

### 规律 2：越需要"上下文理解"的任务，Agent 越能提效

- 看一段代码解释它在做什么 —— Agent 比 IDE 跳转快得多。
- 总结一个长文档 —— Agent 比人工快 10 倍且不会漏。
- 跨文件找问题 —— Agent 比 grep 强太多。

### 规律 3：越需要"判断 + 创造"的任务，Agent 提效最不稳定

- 设计一个新架构 —— Agent 能给方案但不一定是最优。
- 写一段有"风格"的内容 —— Agent 能写但不一定是你的风格。
- 商业决策 —— Agent 能列 pros/cons 但不能替你决策。

### 我的应对

- **标准化、重复性任务**：尽量交给 Agent，我做监督。
- **上下文理解任务**：让 Agent 先跑一遍，我基于结果迭代。
- **判断 + 创造任务**：让 Agent 给多个方案，我来做选择 + 注入领域知识。

## 四、我踩过的坑

### 坑 1：过度信任 Agent 的输出

Agent 写 SQL 时会写出"看起来对但性能很差"的语句。Agent 给的方案经常是"教科书标准答案"，但生产环境有各种约束（数据倾斜、并发限制、现有索引）。

**教训**：永远把 Agent 当"高级实习生"，审稿 + 测试 + 上线必须经过人类关。

### 坑 2：Agent 上下文爆炸

给 Agent 太多上下文，它会"记混"、"抓不住重点"。我曾经把整个 monorepo 的代码塞给 Agent，让它"理解项目"，结果它输出的方案完全跑偏。

**教训**：上下文要"喂重点"，不是"喂全部"。用 RAG 检索 + 重点片段，比塞全文档靠谱。

### 坑 3：忽略 Agent 的"思考税"

Agent 每次思考都要花时间 + token。我曾经让 Agent 对每条用户输入都做"深度分析"，结果响应延迟 30 秒，用户投诉。

**教训**：Agent 不是免费的。简单任务用轻量模型（小模型 + 短 prompt），复杂任务才用大模型 + ReAct。

### 坑 4：Prompt 调优变成"玄学"

我曾经花一整天调 prompt，从 0.7 调到 0.3 反复试，结果发现改动微乎其微。

**教训**：与其调 prompt 不如改流程。给 Agent 更明确的输入格式、更严格的输出 Schema，往往比改 prompt 有效 10 倍。

## 五、给个人开发者的建议

1. **先选 1-2 个工具用深**。Cursor + Claude Code 足够覆盖 80% 个人编码场景。
2. **建立你的 Agent SOP**。把"我每天用 Agent 做什么"写成 SOP，每次优化一点点。
3. **记录你的提效数据**。每周/每月统计"用 Agent 节省了多少时间"，这是继续投入的动力。
4. **警惕"Agent 越多越好"**。我试过同时用 5 个 Agent 工具，最后发现 2-3 个就够。
5. **把 Agent 用成"肌肉"**。每天用、每天迭代，半年后你会发现自己和没用 Agent 的同事效率差距巨大。

---

## 六、本文小结

- 我的工具栈：Cursor + Claude Code + 飞书妙记 + OpenClaw。
- 我的工作流：早上扫、上午深度、中午会议、下午协作、晚上异步。
- 提效规律：标准化 > 上下文理解 > 判断创造。
- 4 个踩过的坑：过度信任、上下文爆炸、思考税、Prompt 玄学。
- 5 条个人建议：选 1-2 个、SOP、数据、克制、肌肉记忆。
