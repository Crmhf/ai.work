# 09 - AI 工程化落地的关键决策

> **TL;DR**：AI 项目能不能落地的关键不是"模型选得多好"，是几个**关键工程决策**做对：自建 vs 采买、单体 vs 多 Agent、全自动 vs 人机协同、按用量 vs 按结果。

---

## 一、为什么大多数 AI 项目失败

我看到的失败模式：

- 模型很好，演示很惊艳，但**生产环境跑不动**（延迟、成本、准确率）。
- 团队很拼，但**做了一年还在 demo 阶段**，没真正进生产。
- 已经上线，但**错误率太高**，用户信任崩溃，最后回到人工。

这些失败的根因不是"AI 不行"，是**工程化决策错了**。

---

## 二、四个关键决策

### 决策 1：自建模型 vs 采买 API

**决策点**：用 OpenAI/Anthropic/国产模型的 API，还是自建 / 微调开源模型。

**自建/微调的好处**：
- 数据不出域（合规要求高的场景）。
- 长期成本可能更低（量大时）。
- 可定制化（领域微调）。

**采买 API 的好处**：
- 起步快，迭代快。
- 不用关心基础设施。
- 能力上限跟着模型厂商升级。

**我的判断框架**：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 早期 MVP / 验证 PMF | 采买 API | 速度优先 |
| 数据敏感（金融、医疗） | 自建/私有化 | 合规优先 |
| 量大（每天百万次调用） | 自建 + 优化 | 成本优先 |
| 通用任务（写文章、总结） | 采买 API | 没必要自建 |
| 垂直领域（法律、医疗） | 采买 API + 微调 | 平衡 |

### 决策 2：单体 Agent vs 多 Agent

**决策点**：一个 Agent 干所有事，还是拆成多个专业化 Agent。

**单体 Agent 的好处**：
- 架构简单，调试容易。
- 没有通信开销。
- 上下文集中。

**多 Agent 的好处**：
- 每个 Agent 更专业。
- 可以并行。
- 错误隔离。

**我的判断框架**：

- **任务能在 8K token 内完成** → 单体 Agent。
- **任务有明显子任务边界** → 多 Agent。
- **需要 7×24 在线** → 多 Agent（容错）。
- **MVP 阶段** → 单体 Agent 先跑起来。

详见 [04 - 多 Agent 协作的边界与陷阱](./04-多Agent协作的边界与陷阱.md)。

### 决策 3：全自动 vs 人机协同

**决策点**：AI 全自动完成任务，还是 AI 做大部分 + 人类把关关键节点。

**全自动的好处**：
- 用户体验流畅。
- 规模化能力强。
- 单位成本低。

**人机协同的好处**：
- 风险可控。
- 错误率低。
- 用户信任容易建立。

**我的判断框架**：

- **风险低 + 量大**（如客服自动回复） → 全自动。
- **风险中**（如代码改动） → 人机协同（Agent 写、人 review）。
- **风险高**（如转账、发外部消息） → 人类必须审批。
- **早期阶段**（PMF 未验证） → 人机协同，先建立信任。

### 决策 4：按用量计费 vs 按结果计费

**决策点**：按 token / 按调用收钱，还是按任务 / 按业务结果收钱。

**按用量的好处**：
- 用户容易理解。
- 起步接受度高。
- 与成本对齐。

**按结果的好处**：
- 用户价值导向，付费意愿高。
- 商业天花板高。
- 倒逼 Agent 提升质量。

**我的判断框架**：

- **早期 / PMF 验证** → 按用量，先把量跑起来。
- **Agent 已经稳定 + 用户付费意愿建立** → 过渡到按结果。
- **垂直场景（高价值）** → 一开始就按结果（法律、销售、医疗）。

---

## 三、决策的时机比决策本身更重要

比"选哪个"更重要的是"什么时候选"。

### 错误的时机
- **MVP 还没跑通就自建模型** → 资源浪费在"非核心"环节。
- **用户量还没起来就追求全自动** → 风险敞口大，迭代慢。
- **PMF 还没验证就按结果计费** → 用户不敢用，量起不来。

### 正确的时机
- **先按用量把 MVP 跑起来** → 用真实数据验证 PMF。
- **PMF 验证后再优化模型**（自建 / 微调）→ 用真实数据决定优化方向。
- **信任建立后再减少人类把关** → 用真实反馈决定自动化边界。
- **量稳定后再改成按结果计费** → 用真实价值决定定价。

## 四、一个真实案例

我自己的一个项目（飞书会议 Agent）的决策时间线：

| 时间 | 决策 | 理由 |
|---|---|---|
| 第 1 周 | 用 OpenAI API | 速度优先 |
| 第 2 周 | 单体 Agent | 任务还在 8K token 内 |
| 第 4 周 | 加人类把关 | 错误率高，先建立信任 |
| 第 8 周 | 拆成 3 个 Agent | 任务变复杂（会议 → 任务 → 表格） |
| 第 12 周 | 微调垂直模型 | 量大且稳定后，成本敏感 |
| 第 16 周 | 改成按"会议处理次数"计费 | 价值明确，按用量过度 |

每次决策都基于"上一阶段已经验证的事实"，不基于"未来的想象"。

---

## 五、AI 工程化落地的 5 个共性原则

1. **真实数据驱动决策**：所有决策都基于已验证的事实，不基于"未来的想象"。
2. **最小可行先跑起来**：先跑通 MVP，再逐步优化，不要在"完美架构"上耗时间。
3. **错误成本决定自动化程度**：错误成本高的场景必须人类把关。
4. **工程化肌肉与模型能力同步补**：监控、调试、回滚这些工程能力不能等"模型更好了再做"。
5. **商业模式与产品形态同步演进**：Copilot 不能用 Agent 的定价，反之亦然。

---

## 六、本文小结

- 四个关键决策：模型选择、单体 vs 多 Agent、自动 vs 协同、计费方式。
- 每个决策都有框架，但**时机比选择更重要**。
- 真实案例：飞书会议 Agent 的 6 个决策时间线。
- 5 个共性原则：真实数据驱动、MVP 优先、错误成本对齐、工程同步、商业模式同步。
