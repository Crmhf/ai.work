# 02 - 我对 Agent 的认知演化

> **TL;DR**：我对 Agent 的认知经历了"工具 → 同事 → 自主体"三跳。每跳背后都是产品形态的重构，不是渐进升级。

---

## 起点：Agent 就是工具（2023 上半年）

我最早用 GPT-4 的 Code Interpreter 跑数据分析时，第一反应是：

> "这就是个更聪明一点的工具，跟 Excel、Tableau 没本质区别。"

那个阶段我对 Agent 的理解是：
- **本质**：自然语言接口的编程工具。
- **价值**：降低使用门槛，让"不会写代码的人"也能完成以前必须编程的任务。
- **局限**：一次性任务，无法持续运行，无法跨任务记忆。

这一阶段我主要在用 Agent 做**单点提效**：写 SQL、写正则、写一段文案、做一次翻译。

---

## 转折：Agent 像半个同事（2023 下半年）

让我转变的是两个观察：

### 观察 1：Cursor Composer 改变了我的编码方式

Composer 不是更聪明的代码补全，它让我可以**用自然语言描述一个完整功能**——"在这个文件里加一个导出按钮，调用后端 /api/export 接口，loading 时禁用按钮，错误时弹 toast"。它能跨文件、跨函数完成。

这不再是工具使用，这是**任务委托**。

### 观察 2：飞书妙记改变了我的会议方式

妙记录制 + AI 提取待办，让会议结束的瞬间我就拿到了结构化的任务清单。

这不再是事后整理，这是**会议与执行的桥接**。

两个观察让我意识到：

> **Agent 不再是工具，它开始扮演"流程中的一个角色"——可以被分配任务、可以交付产出、可以承担重复劳动。**

这就是"同事"的感觉。

---

## 重构：Agent 是自主体（2024 起）

再往后，我开始接触**多 Agent 编排**（OpenClaw、AutoGen、MetaGPT），看到 Orchestrator + Specialist Fleet 这种模式时，我意识到：

> Agent 不只是"被指派的同事"，它可以**自己组织工作**——Orchestrator 接到一个模糊需求，自己拆任务、自己分配、自己质检、自己回滚修复。

这时 Agent 的角色是：
- **独立决策**：在授权范围内自主选择工具和方法。
- **持续运行**：7×24 在线，不是"我打开它才工作"。
- **协作网络**：多个 Agent 通过"产物"而非"对话"协作。

这一阶段的核心挑战从"模型够不够聪明"变成**"工程化能不能扛住生产"** —— 监控、调试、可观测、异常恢复、成本控制。

---

## 三跳背后的产品形态重构

每跳都不只是"更智能"，而是**产品形态的重构**：

| 阶段 | 形态 | 用户心智 | 商业模型 | 主要风险 |
|---|---|---|---|---|
| 工具 | Chat 界面 | 我用 AI 完成一个任务 | 按 token 计费 | 工具不解决问题 |
| 同事 | Agent 平台 | 我分配任务给 AI 同事 | 按席位/任务计费 | 任务理解错位 |
| 自主体 | Agent 团队 | 我管理一支 AI 团队 | 按业务结果/价值计费 | 失控/成本爆炸 |

注意第三行的"商业模型"——一旦 Agent 变成自主体，定价就不能按 token 了，得按**业务结果**。这是商业模式的重构，不是单纯的功能升级。

---

## 我现在的认知

- **单体 Agent 已经成熟到能跑生产**。但工程门槛不低，需要"质量门禁 + 可观测 + 自愈"三件套。
- **多 Agent 协作是必然方向**，但当前阶段更适合"内部工具 + 标准化流程"，不适合"开放场景 + 创造性任务"。
- **AGI 不会从单体 Agent 演进而来**，更可能从"局部自主体网络"逐步涌现。

---

## 写给自己

认知演化最大的教训：**不要用旧范式的心智理解新范式的产物**。

把 Agent 当工具用，永远只能拿到工具的天花板；把它当同事、当自主体，才会看到对应的产品形态与商业机会。
