# 10 - 部署与渐进式采用路径

> **TL;DR**：多 Agent 编排系统的部署不是"装上 OpenClaw 就完事"，是**渐进式采用**——从单 Agent 跑通开始，逐步加 Specialist、加 Orchestrator、加自动化。基础设施和团队能力都要同步建设。

---

## 一、为什么不能"一步到位"

很多团队看了多 Agent 编排的演示很兴奋，立刻想"全员上多 Agent"。**这是错的**。

错误的原因：

### 原因 1：基础设施没准备好

多 Agent 编排需要：
- 共享存储（Git / 对象存储）。
- 消息队列（任务分发）。
- Trace 系统（OpenTelemetry + Jaeger）。
- 监控（Prometheus + Grafana）。
- 告警（PagerDuty / 钉钉 / 飞书）。

没有这些基础设施，多 Agent 系统跑起来"看不到、控不住、修不了"。

### 原因 2：团队能力没准备好

多 Agent 编排需要：
- 工程师理解 LLM 能力边界。
- 工程师掌握 Agent 工程化模式。
- Prompt 调优能力。
- 故障排查能力。

团队没准备好就直接上 → 大量"玄学调参"，最后放弃。

### 原因 3：业务流程没准备好

多 Agent 系统适合"标准化、有 SOP"的任务。如果业务流程本身就混乱，再多 Agent 也只是"加速混乱"。

## 二、渐进式采用路径

### 阶段 0：基础准备（1-2 个月）

**目标**：基础设施和团队就绪。

**必做项**：

1. **基础设施**
   - 部署 OpenClaw Gateway（独立服务，集群化）。
   - 搭建共享存储（Git + 对象存储）。
   - 部署 Trace 系统（OpenTelemetry + Jaeger）。
   - 部署监控系统（Prometheus + Grafana）。
   - 部署日志系统（ELK 或 Loki）。
   - 配置告警（PagerDuty / 钉钉机器人）。

2. **团队能力**
   - 工程师培训（OpenClaw 基础、Agent 设计模式）。
   - Prompt 工程培训（少样本、思维链、约束）。
   - 建立内部"Agent 最佳实践"文档。

3. **第一个试点项目**
   - 选一个**简单、重复、有明确输入输出**的任务。
   - 例：批量文档摘要、批量数据清洗、批量测试用例生成。

**成功标准**：
- 单 Agent 能稳定跑通试点任务。
- 监控、Trace、告警都正常工作。
- 团队对 OpenClaw 有基本使用经验。

---

### 阶段 1：单 Agent 成熟（2-3 个月）

**目标**：1-2 个 Agent 在生产环境稳定运行。

**必做项**：

1. **完善 Agent 配置**
   - SOUL.md 完整（Identity、Capabilities、Rules、Tools）。
   - 输入输出契约明确（schema 化）。
   - 错误处理完善（重试、回滚、升级）。

2. **完善质量门禁**
   - 每个 Agent 的产出都有质量检查。
   - 自动重试 + 自愈机制。
   - 失败时自动升级人工。

3. **完善可观测性**
   - 每个 Agent 调用都有 Trace。
   - 每个 Agent 都有 Metrics。
   - 每个 Agent 失败都有 Alert。

**成功标准**：
- 1-2 个 Agent 7×24 稳定运行。
- 错误率 < 5%，自愈成功率 > 70%。
- 团队对 Agent 调优有经验。

---

### 阶段 2：Orchestrator 引入（3-4 个月）

**目标**：Orchestrator 能调度 2-3 个 Specialist Agent。

**必做项**：

1. **任务分解**
   - 基于模板的任务分解（项目模板、任务模板）。
   - LLM 实例化模板生成具体任务。
   - DAG 构建与循环检测。

2. **调度决策**
   - 串行/并行/波次/条件/HITL 五种模式。
   - 状态机驱动调度。
   - 异常恢复机制。

3. **质量门禁扩展**
   - 每个 wave 完成时检查门禁。
   - 不通过则自动回溯修复（最多 3 次）。
   - Bug 修复循环。

4. **HITL 节点**
   - 在关键决策点（PRD 确认、架构评审、上线审批）设置人工审批。

**成功标准**：
- Orchestrator 能调度 2-3 个 Specialist 跑通完整流程。
- HITL 节点正常工作（审批及时、流程不卡）。
- 自愈机制有效（大部分错误自动修复）。

---

### 阶段 3：多 Agent 团队（4-6 个月）

**目标**：完整的 6-7 个 Agent 团队，端到端自动化项目交付。

**必做项**：

1. **完整 Agent 团队**
   - Product / UI Designer / Architect / Coder Frontend / Coder Backend / QA / DevOps。
   - 每个 Agent 都有 SOUL.md + 契约 + 门禁。

2. **完整 Lobster 工作流**
   - 复杂项目的完整工作流定义。
   - 错误处理完整（各类异常都有应对）。
   - 完成动作（通知、汇总、归档）。

3. **完整监控**
   - 项目级 + 系统级仪表盘。
   - 多维度告警（任务、成本、质量、性能）。
   - 自动响应机制。

**成功标准**：
- 完整团队能跑通中小型项目（Web/App/小程序）。
- 端到端时间从"周"缩短到"天"。
- 失败时自动恢复 + 自动升级。

---

### 阶段 4：自演化与定制（6 个月+）

**目标**：多 Agent 系统能根据业务反馈自演化，并支持垂直定制。

**必做项**：

1. **自演化机制**
   - Agent 根据失败案例自动调优 prompt。
   - Orchestrator 根据历史数据优化调度策略。
   - 模板根据项目类型自动扩展。

2. **垂直定制能力**
   - 不同业务线有不同 Agent 配置。
   - 行业知识沉淀（金融、医疗、法律等）。
   - 私有模型 + 私有数据支持。

3. **生态开放**
   - 第三方 Agent 可以接入平台。
   - 共享任务模板市场。
   - 标准化 Agent 协议（MCP）。

**成功标准**：
- 系统能自我优化（不需要工程师手动调优）。
- 多个业务线在平台上独立运行。
- 外部 Agent 可以接入。

## 三、基础设施方案

### 小规模（个人 / 小团队）

```
┌──────────────────────────────┐
│   OpenClaw CLI (本地)        │
│   - 1-3 Agent                │
│   - 文件共享                 │
│   - 本地日志                 │
└──────────────────────────────┘
```

- 单机部署 OpenClaw CLI。
- 用本地文件系统作为共享存储。
- 用 Git 追踪产物。
- 日志输出到终端或本地文件。
- 适合：个人项目、小团队内部工具。

---

### 中等规模（部门级）

```
┌────────────────────────────────────────────┐
│         OpenClaw Gateway（集群）           │
│         - 多实例负载均衡                    │
│         - Agent Pool                       │
└────────────────────────────────────────────┘
                    │
                    ▼
┌────────────────────────────────────────────┐
│   共享存储（Git + S3/MinIO）               │
│   Trace（OpenTelemetry + Jaeger）          │
│   Metrics（Prometheus + Grafana）          │
│   Logs（ELK）                              │
└────────────────────────────────────────────┘
```

- OpenClaw Gateway 集群部署（K8s）。
- 用 S3/MinIO 做对象存储（产物、模型文件）。
- 完整可观测性栈。
- 适合：企业部门级应用。

---

### 大规模（企业级）

```
┌─────────────────────────────────────────────┐
│              API Gateway                     │
│   (认证 / 限流 / 路由 / 审计)               │
└──────────────────┬──────────────────────────┘
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
┌────────────┐ ┌────────────┐ ┌────────────┐
│ Orchestrator│ │Orchestrator│ │Orchestrator│
│  Tenant A   │ │  Tenant B  │ │  Tenant C  │
└──────┬──────┘ └──────┬──────┘ └──────┬──────┘
       │               │               │
       └───────────────┼───────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│   共享服务层                                  │
│   - Agent Pool（K8s）                        │
│   - 模型服务（多模型路由）                   │
│   - 存储服务（Git + S3 + 向量 DB）           │
│   - 监控服务（Metrics + Logs + Traces）      │
│   - 安全服务（认证 + 加密 + 审计）           │
└─────────────────────────────────────────────┘
```

- 多租户架构（不同业务线隔离）。
- API Gateway 统一入口。
- 共享 Agent Pool（弹性扩缩容）。
- 多模型路由（不同 Agent 用不同模型）。
- 完整的安全 + 审计 + 合规。

## 四、团队组建建议

### 阶段 0-1 团队（2-3 人）
- **1 个 Agent 工程师**：负责 OpenClaw 配置、Agent 开发、Prompt 调优。
- **1 个后端工程师**：负责基础设施、监控、CI/CD。
- **1 个领域专家**：提供业务知识，定义任务模板。

### 阶段 2-3 团队（4-6 人）
- 在阶段 0-1 基础上加：
- **1 个前端工程师**：负责 Web UI、CLI 工具。
- **1 个 QA 工程师**：负责测试 Agent、自动化测试。
- **1 个 DevOps 工程师**：负责 K8s、监控、告警。

### 阶段 4 团队（8-12 人）
- 在阶段 2-3 基础上加：
- **2-3 个领域专家**：覆盖多个业务线。
- **1 个数据科学家**：负责模型选择、微调、评估。
- **1 个产品经理**：负责 Agent 产品化、用户研究。

## 五、风险与应对

### 风险 1：成本爆炸

Agent 调用 LLM API 成本可能远超预期。

**应对**：
- 设置每日/每项目 Token 预算。
- 超过预算自动降级（小模型 / 短 prompt）。
- 关键决策用大模型，简单任务用小模型。

### 风险 2：错误扩散

一个 Agent 错误传播到下游，导致整个项目失败。

**应对**：
- 每个 wave 完成后立即检查门禁。
- 错误立即回溯，不让错误扩散。
- 关键产物有版本控制（git revert）。

### 风险 3：失控循环

Agent 进入死循环，消耗大量 Token 但没产出。

**应对**：
- 单任务超时（30 分钟）自动中断。
- 单任务重试上限（3 次）。
- 死循环检测（Agent 输出相似度检测）。

### 风险 4：HITL 不及时

人工审批节点超时未处理，流程卡住。

**应对**：
- HITL 节点必须有 timeout。
- 超时自动升级（下一个审批人 / 自动通过 / 自动拒绝，根据业务规则）。
- 审批人必须有 SLA（如 24 小时内必须审批）。

## 六、我的实战经验

### 经验 1：阶段 0-1 一定要慢

不要急着上多 Agent。先把单 Agent 跑稳，把基础设施建好。**基础设施和团队能力的成熟度，决定了多 Agent 系统能不能跑起来**。

### 经验 2：第一个试点项目要"小而美"

选一个**简单、重复、有明确输入输出**的任务。成功后建立信心，再扩展到复杂任务。

### 经验 3：HITL 不能太多也不能太少

太多：流程慢，等审批等死人。
太少：关键决策没人把关，错误扩散。

建议：**3-5 个 HITL 节点**，覆盖关键决策点。

### 经验 4：监控比功能重要

监控仪表盘必须**比功能更早上线**。没有监控的系统是"裸奔"。

### 经验 5：成本是头等大事

LLM 成本很容易失控（每次调用 0.1 美元 × 1000 次/天 × 30 天 = 3000 美元/月）。
**必须设置预算 + 自动降级**。

---

## 七、本章关键 takeaway

- 渐进式采用：阶段 0 基础准备 → 阶段 1 单 Agent → 阶段 2 Orchestrator → 阶段 3 完整团队 → 阶段 4 自演化。
- 每个阶段都要"成功标准"，不达标不进入下一阶段。
- 基础设施三档：小规模（单机）、中等规模（集群）、大规模（多租户）。
- 团队组建按阶段扩展。
- 4 大风险：成本爆炸、错误扩散、失控循环、HITL 不及时。
- 经验：阶段 0-1 要慢、第一个项目小而美、HITL 适度、监控优先、成本第一。
