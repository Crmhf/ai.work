# 01 - 多 Agent 编排总览与定位

> **TL;DR**：多 Agent 编排不是"多个 Agent 同时跑"，是**"一个 Orchestrator 调度多个 Specialist，按依赖图分波次执行，通过产物驱动通信，每步有质量门禁"**。这套范式解决"复杂任务端到端自动化"问题。

---

## 一、为什么需要多 Agent 编排

单体 Agent 在简单任务上表现出色，但遇到**复杂、多阶段、需要多个领域知识协作**的任务时会遇到几个问题：

### 问题 1：上下文超载

把"做一个电商小程序"丢给单体 Agent，它要把"产品需求、UI 设计、后端架构、前端开发、测试、部署"全部塞进上下文。结果：
- 关键信息被淹没（"在 8K token 海洋里找一根针"）。
- 推理质量下降（注意力分散）。
- Token 成本爆炸（每次都要重读全部历史）。

### 问题 2：专业化不足

单体 Agent 试图"通吃所有领域"，每个领域都只能做浅。表现就是"看起来做了，但每个环节都不专业"。

### 问题 3：无法并行

单体 Agent 串行执行所有步骤。10 个步骤 × 每个 5 分钟 = 50 分钟。但其中 7 个步骤其实可以并行。

### 问题 4：错误恢复困难

单体 Agent 出错时，从头再来。多 Agent 系统可以**只重跑出错的那部分**。

---

## 二、多 Agent 编排解决什么问题

多 Agent 编排（Multi-Agent Orchestration）是解决以上问题的工程范式，核心思路：

### 思路 1：Orchestrator 拆活 + Specialist 干活

- **Orchestrator（指挥官）**：理解用户意图、拆任务、定依赖、调度、质检、回滚。
- **Specialist（专家）**：在特定领域内做深（产品、UI、架构、编码、测试、部署）。
- **Reviewer（审核员）**：统一质量门禁，避免 Specialist "自评自夸"。

### 思路 2：产物驱动通信

- Specialist 之间**不直接对话**，通过**共享存储 + 契约产物**通信。
- A 完成任务把产物写到 `shared/02_UI/HomePage.md`，B 读这个文件继续。
- 通信开销降到最低，调试复杂度降到最低。

### 思路 3：DAG 驱动调度

- 所有任务分解为有向无环图（DAG）。
- 同一波次（wave）的任务可并行。
- 跨波次串行（依赖关系决定顺序）。

### 思路 4：质量门禁 + 自愈

- 每个阶段有"质量门禁"（PRD 完整性、测试覆盖率、代码 lint 等）。
- 不通过自动回溯修复，最多 3 轮。
- 3 轮还不通过，升级到人类。

## 四、典型工作流

以"做一个电商小程序"为例，多 Agent 编排的典型工作流：

```
Wave 1: 需求澄清（如果需要）
Wave 2: PRD 编写（Product Agent）
Wave 3: 设计系统 + 架构（UI Agent + Architect Agent，并行）
Wave 4: 详细设计 + API Spec（UI Agent + Architect Agent，并行）
Wave 5: 编码实现（Frontend Coder + Backend Coder，并行）
Wave 6: 测试验证（QA Agent）
Wave 7: 部署交付（DevOps Agent）
```

每一步都有质量门禁。如果某步不通过，自动回溯到前序 Agent 修复（最多 3 轮）。

## 五、适用场景与不适用场景

### 适合 ✅

- **中小型全栈应用**（Web/App/小程序）的端到端开发
- **MVP 快速原型**的构建与迭代
- **已有产品的功能模块**扩展与重构
- **技术栈统一、架构清晰**的标准化项目

### 不适合 ❌

- **强实时性系统**（Agent 调度有秒级延迟）
- **强合规、强审计场景**（Agent 决策不可解释风险）
- **超大规模并发**（千级以上 Agent 协同未验证）
- **高创造性任务**（写作、设计风格 —— 这类任务 Specialist 难以形式化）

---

## 六、OpenClaw 在这个范式中的角色

OpenClaw 是**多 Agent 协作框架**，提供了：
- **Agent 隔离**：每个 Agent 是独立进程，独立上下文。
- **会话路由**：`sessions_send` 让 Orchestrator 给任意 Agent 发消息。
- **共享存储**：所有 Agent 共享文件系统 + Git。
- **可观测性**：所有调用有 trace。
- **Lobster DSL**：把多 Agent 编排写成可执行 YAML。

但 OpenClaw **不提供**：
- 任务分解算法（需要 Orchestrator 自己实现）
- 质量门禁规则（需要按业务定义）
- 领域知识（需要每个 Specialist 自己配置 SOUL.md）

所以 OpenClaw 是"基础设施"，业务编排逻辑由 Orchestrator Agent 决定。

---

## 七、本章关键 takeaway

- 多 Agent 编排 = Orchestrator + Specialist Fleet + 产物驱动 + DAG 调度 + 质量门禁。
- 解决：上下文超载、专业化不足、串行慢、错误恢复难。
- 适合：标准化、有 SOP 的端到端任务。
- 不适合：强实时、强合规、高创造性任务。
- OpenClaw 提供框架，业务编排由 Orchestrator 决定。
