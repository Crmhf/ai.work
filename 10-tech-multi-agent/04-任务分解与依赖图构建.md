# 04 - 任务分解与依赖图构建

> **TL;DR**：任务分解是多 Agent 编排的"第一公里"。分解得好，系统跑得快；分解得差，系统跑不动。核心是**意图解析 → 模板匹配 → 实例化 → DAG 构建 → 波次划分**五步。

---

## 一、任务分解的 5 步流程

Orchestrator 接收到用户需求后，按以下流程分解：

```
用户输入: "做一个电商小程序，包含商品展示、购物车、下单支付"
    │
    ▼
[Step 1] 意图解析 → 识别项目类型、规模、技术偏好约束
    │
    ▼
[Step 2] 阶段分解 → 标准软件工程生命周期阶段
    │   ├─ Phase 1: 需求与产品规划
    │   ├─ Phase 2: UI/UX 设计
    │   ├─ Phase 3: 技术架构设计
    │   ├─ Phase 4: 工程实现（前端 + 后端）
    │   ├─ Phase 5: 测试验证
    │   └─ Phase 6: 部署交付
    │
    ▼
[Step 3] 任务原子化 → 每个阶段拆分为原子任务（1-4小时工作量）
    │   例: Phase 2 拆分为:
    │   ├─ Task 2.1: 设计系统定义
    │   ├─ Task 2.2: 首页线框图
    │   ├─ Task 2.3: 商品详情页线框图
    │   ├─ Task 2.4: 购物车页线框图
    │   ├─ Task 2.5: 下单流程线框图
    │   └─ Task 2.6: 交互规范与组件清单
    │
    ▼
[Step 4] 依赖分析 → 建立 DAG（有向无环图）
    │   Task 2.2~2.5 依赖 Task 2.1
    │   Task 4.1（前端开发）依赖 Task 2.x 和 Task 3.x
    │
    ▼
[Step 5] 波次划分 → 同层任务可并行
```

---

## 二、Step 1：意图解析

### 目标

从用户模糊输入提取结构化信息。

### 实现

```python
def analyze_intent(requirement: str) -> Dict:
    prompt = f"""
    分析以下用户需求，提取关键信息：
    
    需求: {requirement}
    
    请输出 JSON 格式：
    {{
        "project_type": "webapp|mobile_app|mini_program|api_service",
        "target_platform": ["web", "ios", "android", "wechat_mini"],
        "core_features": ["feature1", "feature2"],
        "user_scale": "small|medium|large",
        "tech_preferences": ["react", "node.js"],
        "constraints": ["budget_limit", "timeline"],
        "ambiguity_flags": ["unclear_auth_flow", "missing_payment_detail"]
    }}
    """
    return json.loads(llm.generate(prompt, format="json"))
```

### 关键要点

1. **必须显式提取 `ambiguity_flags`**。如果意图有歧义，**主动追问用户**而不是猜测。
2. **项目类型必须从有限集合中选**（webapp / mobile_app / mini_program / api_service），便于匹配模板。
3. **技术偏好若有冲突**（如"既要 React 又要 Vue"），标记为 ambiguity。

### 反模式

- ❌ 让 LLM 自由发挥任务分解 → 输出无法结构化。
- ❌ 不提取 ambiguity → Agent 猜错后返工成本高。
- ❌ 字段过多（如"必须填 20 个字段"）→ 意图解析本身变得不可靠。

## 三、Step 2：模板选择

### 目标

基于项目类型选择预定义的"项目模板"，避免每次都从零分解。

### 模板示例（webapp）

```yaml
# templates/webapp_template.yaml

  type: "webapp"
  phases:
    - id: "P1"
      name: "Product Planning"

          outputs: ["DesignSystem.md"]

        - template_id: "design_pages"
          outputs: ["Wireframes/*"]
          depends_on: ["define_design_system"]
        - template_id: "interaction_specs"
          outputs: ["InteractionSpecs.md"]

    - id: "P3"
      name: "Architecture"
```

### 关键要点

- 模板是**预定义的骨架**，但任务细节由 LLM 基于意图实例化。
- 每个模板任务有 `template_id`、`default_duration_hours`、`depends_on`、`outputs`。
- 模板按项目类型准备多套：webapp、mobile_app、mini_program、api_service。

## 四、Step 3：任务原子化

### 目标

把模板任务"实例化"为具体的原子任务（1-4 小时工作量）。

### 实现

```python
def instantiate_template(template: Dict, intent: Dict) -> List[Task]:
    prompt = f"""
    基于以下模板和项目意图，生成具体的任务分解方案：
    
    模板: {yaml.dump(template)}
    
    项目意图: {json.dumps(intent, ensure_ascii=False)}
    
    要求：
    1. 每个任务必须是可独立执行的（1-4 小时工作量）
    2. 明确每个任务的输入依赖和输出产物
    3. 技术栈选择必须符合用户偏好
    4. 如果意图中有 ambiguity_flags，生成澄清任务而非猜测
    5. 输出 YAML 格式的任务列表
    """
    tasks_yaml = llm.generate(prompt, format="yaml")
    return parse_tasks(tasks_yaml)
```

### 输出示例

```yaml
# project_dag.yaml
project:
  name: "ecommerce-miniapp"

  - id: "P1"

      - id: "T2.2"

```

### 关键要点

- 每个任务必须有 `id`、`agent`、`estimated_duration_minutes`、`dependencies`、`inputs`、`outputs`、`guardrails`。
- 任务粒度 1-4 小时。太小（< 30 分钟）说明过度分解；太大（> 4 小时）说明分解不够。
- `guardrails` 是质量门禁的前置条件，详见 [`08-质量门禁与自愈机制.md`](./08-质量门禁与自愈机制.md)。

## 五、Step 4：DAG 构建

### 目标

构建有向无环图（DAG），确保依赖关系正确。

### 核心算法：DFS 检环

```python
def has_cycle(tasks: List[Task]) -> bool:
    """DFS 检测循环依赖"""
    WHITE, GRAY, BLACK = 0, 1, 2
    color = {t.id: WHITE for t in tasks}
    task_map = {t.id: t for t in tasks}
    
    def dfs(node_id: str) -> bool:
        color[node_id] = GRAY
        for dep_id in task_map[node_id].dependencies:
            if color[dep_id] == GRAY:
                return True  # 循环！
            if color[dep_id] == WHITE and dfs(dep_id):
                return True
        color[node_id] = BLACK
        return False
    
    for task in tasks:
        if color[task.id] == WHITE:
            if dfs(task.id):
                return True
    return False
```

### 关键要点

- 必须检测循环依赖（任务 A 依赖 B，B 又依赖 A）。
- 循环依赖必须由 Orchestrator **自动修复**（去掉冗余依赖）或**升级人工**。
- 循环依赖是常见错误，模板配置出错时容易出现。

### 反模式

- ❌ 让 Agent "自己管理依赖关系" → Agent 会写出循环依赖。
- ❌ 不做循环检测 → 调度器会死锁。

## 六、Step 5：波次划分

### 目标

把 DAG 转换为可执行波次：同一波次内的任务可并行，跨波次串行。

### 核心算法：拓扑排序 + 入度递减

```python
def build_waves(tasks: List[Task]) -> List[List[Task]]:
    """将任务按依赖关系分层，生成执行波次。
    同一波次内的任务无相互依赖，可并行执行。"""
    in_degree = {t.id: len(t.dependencies) for t in tasks}
    task_map = {t.id: t for t in tasks}
    waves = []
    remaining = set(t.id for t in tasks)
    
    while remaining:
        # 当前所有入度为 0 的任务（无未满足依赖）
        current_wave_ids = [tid for tid in remaining if in_degree[tid] == 0]
        if not current_wave_ids:
            cycle = find_cycle(task_map, remaining)
            raise CycleError(f"依赖循环: {' -> '.join(cycle)}")
        
        waves.append([task_map[tid] for tid in current_wave_ids])
        remaining -= set(current_wave_ids)
        
        # 减少下游任务的入度
        for tid in current_wave_ids:
            task = task_map[tid]
            for downstream_id in task.downstreams:
                if downstream_id in in_degree:
                    in_degree[downstream_id] -= 1
    
    return waves
```

### 示例输出

```
Wave 1: [T1.1]                  # PRD 编写（仅一个）
Wave 2: [T2.1, T3.1]            # 设计系统 + 系统架构（并行）
Wave 3: [T2.2, T2.3, T2.4, T3.2] # 各页面线框图 + API Spec（并行）
Wave 4: [T4.1, T4.2]            # 后端 + 前端实现（并行）
Wave 5: [T5.1, T5.2]            # 单元测试 + 集成测试（并行）
Wave 6: [T6.1]                  # 部署
```

### 关键要点

- 每个 wave 内任务可并行。
- wave 间必须串行（下 wave 等上 wave 全部完成）。
- wave 数量越少越好（说明并行度高）。
- 单个 wave 任务数量最好 < 5（避免资源抢占）。

### 性能估算

```
总时长 = Σ(wave 内最长任务) + wave 间串行开销

优化方法：
- 让 wave 内任务时长尽量均衡（避免一个长任务拖整个 wave）
- 让关键路径任务优先（关键路径 = 总时长决定项）
```

## 七、实战踩坑点

### 坑 1：模板粒度太粗

如果模板里"前端实现"是单个任务（16 小时），就失去了"细粒度并行"的机会。

**解决**：模板粒度按"1-4 小时"切分，不要嫌麻烦。

### 坑 2：依赖过紧

任务 B 只需要任务 A 的某个字段，但被标记为"完全依赖 A"。

**解决**：明确依赖的是"哪个产物"（不是"哪个任务"），如 `["shared/01_PRD/PRD.md"]` 而非 `["T1.1"]`。

### 坑 3：循环依赖未及时发现

模板配置错误导致循环依赖（DAG 不再是无环图）。

**解决**：构建 DAG 后**必须**调用 `has_cycle` 检查；不通过则报错或升级人工。

### 坑 4：wave 划分不均

一个 wave 1 个任务，另一个 wave 10 个任务，导致资源浪费或抢占。

**解决**：手动调整模板，或在波次划分后做"负载均衡"。

---

## 八、本章关键 takeaway

- 任务分解 5 步：意图解析 → 模板选择 → 实例化 → DAG 构建 → 波次划分。
- 意图解析必须显式提取 ambiguity，主动追问用户。
- 模板是预定义骨架，具体任务由 LLM 实例化。
- DAG 必须做循环检测，避免调度死锁。
- 波次划分算法：拓扑排序 + 入度递减。
- 实战踩坑：模板粒度、依赖过紧、循环依赖、wave 不均。
