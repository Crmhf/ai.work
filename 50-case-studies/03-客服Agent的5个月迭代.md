# 03 - 客服 Agent 的 5 个月迭代

> **TL;DR**：一个客服 Agent 从 demo 到生产**经历了 5 个月迭代**，处理 70% 一线问题，每月节省人工 60+ 工时。本篇记录完整迭代过程，重点讲"为什么每个版本都比上个版本好"。

---

## 一、起点：第 1 版（demo 惊艳）

### 时间

第 1-2 周。

### 目标

做出一个"看起来能用"的 demo，给老板演示。

### 方案

- 单 Agent + LangChain + OpenAI API。
- 用 GPT-4 处理所有客户问题。
- 无质量门禁、无 HITL、无监控。

### 效果

- **Demo 成功率**：95%+（精心准备的测试问题）。
- **真实用户测试**：2 天后被打回。错误率 35%+。

### 失败原因

- 用户问题千奇百怪，超出 prompt 覆盖范围。
- LLM 幻觉（编造公司政策）。
- 无错误日志，出错无法调试。

### 教训

> **demo 成功 ≠ 生产成功**。真实场景的复杂度是 demo 的 10 倍。

---

## 二、第 2 版：加入 RAG + 知识库

### 时间

第 3-4 周。

### 改进

- 接入公司知识库（产品文档、政策文档、FAQ）。
- 用 RAG 检索相关内容喂给 LLM。
- 加入 Prompt 约束"如果知识库没答案，必须说不知道"。

### 效果

- **幻觉率**：从 35% 降至 12%。
- **回答准确率**：从 65% 提升到 85%。
- **仍然失败**：用户问"产品 A 能不能退款"时，LLM 直接回答"可以"（公司政策是不能退）。

### 失败原因

- RAG 检索到了相关文档，但 LLM 没"读懂"政策细节。
- 缺少**答案验证**步骤。

### 教训

> RAG 不能解决所有问题。**LLM 必须验证答案与知识库的一致性**。

---

## 三、第 3 版：加入答案验证 + HITL

### 时间

第 5-8 周。

### 改进

- 答案生成后，加一层"验证 Agent"，检查答案与知识库是否一致。
- 不一致或低置信度的答案，升级到 HITL（人工客服）。
- HITL 节点 SLA：5 分钟内必须响应。

### 效果

- **错误率**：从 15% 降至 5%。
- **人工接管率**：25%（比预期高，但可接受）。
- **用户满意度**：从 60% 提升到 78%。

### 仍然失败

- 高峰期 HITL 客服忙不过来，SLA 经常超时。
- 用户等太久，投诉。

### 教训

> **HITL 节点必须有 SLA + 升级路径**，否则系统脆弱。

---

## 四、第 4 版：分层处理 + 路由

### 时间

第 9-12 周。

### 改进

- 引入**路由器 Agent**：先分类用户问题。
- 不同类别走不同处理路径：
  - **简单 FAQ**（订单查询、政策咨询）→ LLM 直接回答。
  - **中等复杂度**（退款、技术问题）→ LLM + 答案验证，置信度高才回答。
  - **复杂问题**（投诉、纠纷）→ 直接 HITL。
- 高峰期动态调整 HITL 配额。

### 效果

- **错误率**：从 5% 降至 2%。
- **人工接管率**：从 25% 降至 12%。
- **平均响应时间**：从 90 秒降至 30 秒。
- **用户满意度**：从 78% 提升到 88%。

### 仍然失败

- 个别"边缘案例"仍出错。
- LLM 偶尔会"过度自信"（明明知识库没答案，但 LLM 编造）。

### 教训

> **分层处理是必要的**。把所有问题都丢给同一个 Agent 是反模式。

---

## 五、第 5 版：加入反馈闭环 + 自动调优

### 时间

第 13-20 周。

### 改进

- 用户反馈按钮（👍 / 👎）。
- 失败 case 自动收集 → 人工标注 → 自动加入训练数据。
- 每周用新数据**自动微调** LLM prompt。
- 加入 A/B 测试（新旧 prompt 各跑 50% 用户）。

### 效果

- **错误率**：从 2% 降至 0.8%。
- **人工接管率**：从 12% 降至 8%。
- **用户满意度**：从 88% 提升到 94%。
- **每月节省**：60+ 工时人工。

### 当前状态（上线 6 个月）

- 70% 一线问题由 Agent 处理。
- 30% 复杂问题人工处理（Agent 提供"建议回答"辅助）。
- 持续监控 + 周级别 prompt 迭代。

---

## 六、5 个月迭代的关键数据

| 版本 | 时间 | 错误率 | 人工接管率 | 满意度 |
|---|---|---|---|---|
| v1 demo | 第 2 周 | 35% | 100% | 60% |
| v2 RAG | 第 4 周 | 12% | 100% | 65% |
| v3 验证 | 第 8 周 | 5% | 25% | 78% |
| v4 路由 | 第 12 周 | 2% | 12% | 88% |
| v5 反馈 | 第 20 周 | 0.8% | 8% | 94% |

---

## 七、5 个月踩的坑

### 坑 1：低估真实场景的复杂度

第 1 版 demo 用了 20 个精心准备的测试问题，全过。第 2 天真实用户测试，错误率 35%。

**教训**：**demo 用例 ≠ 真实分布**。从第一天起就要用真实用户数据测试。

### 坑 2：RAG 不是银弹

第 2 版以为加了 RAG 就能解决幻觉，结果 LLM 还是编造。

**教训**：**RAG + 答案验证**才能真正降幻觉。

### 坑 3：HITL 没有 SLA = 系统脆弱

第 3 版 HITL 节点设计时没考虑 SLA，高峰期崩盘。

**教训**：**HITL 必须有 SLA + 升级机制**。

### 坑 4：所有问题都用同一个 Agent

第 4 版之前，所有问题（简单 FAQ、复杂投诉）都丢给同一个 Agent。

**教训**：**分层处理**才能稳定。

### 坑 5：没收集失败案例

第 1-4 版没系统收集失败案例，调优靠"猜"。

**教训**：**反馈闭环**是 Agent 持续改进的关键。

---

## 八、关键经验

### 1. Agent 项目是"持续迭代"，不是"一次交付"

5 个月迭代 5 个版本，每个版本都比上个好 30%+。**Agent 项目的成功 = 持续迭代能力**。

### 2. 数据驱动调优

不要靠"我觉得 prompt 不好"。**靠用户反馈数据 + 自动标注** 调优。

### 3. 简单场景先跑通

第 1 版先做简单 FAQ，第 4 版才加复杂场景。**从简单到复杂**。

### 4. HITL 是过渡，不是终极方案

第 5 版人工接管率仍有 8%，但**逐年降低**。HITL 是"过渡方案"，终极目标是全自动。

### 5. 用户反馈是最宝贵的数据

👍 / 👎 反馈、自动收集失败案例 → 标注 → 训练数据 → prompt 改进。**闭环**才是关键。

---

## 九、本章关键 takeaway

- 客服 Agent 从 demo 到生产用了 5 个月，**5 个版本迭代**。
- 错误率从 35% 降到 0.8%，用户满意度从 60% 升到 94%。
- **每次迭代都解决一个明确问题**：幻觉 → RAG → 验证 → 路由 → 反馈。
- **demo 成功 ≠ 生产成功**，真实场景复杂度是 demo 的 10 倍。
- **HITL 必须有 SLA**，分层处理是必要的，反馈闭环是关键。
- **Agent 项目的成功 = 持续迭代能力**，不是一次交付。
