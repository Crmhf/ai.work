# 02 - 飞书会议 Agent 在创业公司的应用

> **TL;DR**：一个 50 人创业公司部署飞书会议 Agent 6 个月后，**会议纪要→任务落地率从 50% 提升到 92%**，平均每周节省 8 小时人工。本篇是真实部署复盘。

---

## 一、背景

### 公司情况

- **行业**：B2B SaaS（在线协作工具）。
- **规模**：50 人（10 个工程师 + 15 个销售 + 10 个运营 + 15 个职能）。
- **痛点**：
  - 会议多（每周约 30 场）。
  - 会议产出难落地（待办散落在纪要里）。
  - 跟进效率低（PM 手动从纪要提取任务）。

### 目标

用飞书生态 + AI 实现：
- 会议结束自动产出纪要（结构化）。
- 自动提取待办 → 自动创建飞书任务。
- 任务进展自动回写到多维表格。
- PM 看多维表格就能掌握全局。

---

## 二、方案

### 整体架构

```
会议（飞书）
    ↓ 录制 + 妙记 AI
妙记 AI 产物（summary + todo_list + sections）
    ↓ 定时轮询（5 分钟）
[任务同步引擎] 提取待办 → 创建飞书任务（含 origin）
    ↓
[多维表格同步] 任务状态变更 → Automation Webhook → 回写
    ↓
业务数据（多维表格：项目主表 + 任务跟踪表）
```

### 三层混合架构

- **第一层：API**——妙记 AI 产物 + 任务 API + 多维表格 API。
- **第二层：Automation**——多维表格变更 Webhook 桥接。
- **第三层：定时补偿**——每 5 分钟对账。

---

## 三、实施过程

### 第 1-2 周：基础设施

- 创建飞书自建应用，申请高级权限（妙记、任务、多维表格、会议）。
- 配置多维表格（项目主表 + 任务跟踪表 + 客户反馈表）。
- 部署后端服务（FastAPI + Redis + Celery）。

**关键耗时**：权限审核 4 个工作日（计划预留 3-5 天，符合预期）。

### 第 3-4 周：MVP 跑通

- 实现妙记 AI 产物提取（轮询 + 解析）。
- 实现任务自动创建（含 origin 溯源）。
- 实现多维表格初始化（每场会议登记一行）。

### 第 5-6 周：双向同步

- 实现 Automation Webhook 接收。
- 实现任务状态变更 → 多维表格回写。
- 实现定时补偿任务（5 分钟）。

### 第 7-8 周：上线 + 培训

- 灰度上线（仅工程师团队）。
- 培训所有员工。
- 全量上线。

---

## 四、量化结果（6 个月后）

### 会议纪要落地率

| 指标 | 上线前 | 上线后 | 提升 |
|---|---|---|---|
| 任务落地率（每场会议的待办变成飞书任务的比例） | 50% | 92% | +42pp |
| 平均每场会议产出的任务数 | 2.1 | 3.8 | +81% |
| 任务完成率（任务被按时完成的比例） | 60% | 78% | +18pp |

### 时间节省

| 工作 | 上线前 | 上线后 | 节省 |
|---|---|---|---|
| PM 手动提取待办 | 5 小时/周 | 0 小时/周 | 5 小时/周 |
| 员工手动整理纪要 | 8 小时/周 | 1 小时/周 | 7 小时/周 |
| 跟进任务进展 | 6 小时/周 | 2 小时/周 | 4 小时/周 |
| **总节省** | **19 小时/周** | **3 小时/周** | **16 小时/周** |

**月节省**：64 小时 ≈ 0.8 FTE。

### 业务指标

- **销售跟进及时率**：从 70% 提升到 88%。
- **客户反馈响应时间**：从平均 4 小时缩短到 30 分钟。
- **项目延期率**：从 35% 降低到 18%。

## 五、踩过的坑

### 坑 1：妙记 AI 提取准确率不稳定

**现象**：早期测试时，妙记 AI 提取的待办有 15% 不准确（漏掉或多提）。

**原因**：会议内容质量差（多人抢话、无明确分工）。

**解决**：
- 培训会议主持人（明确"我说的事由 XX 负责"句式）。
- 增加"会前议程"环节（让 AI 更好理解）。
- 准确率从 85% 提升到 95%+。

### 坑 2：定时轮询造成 API 限流

**现象**：高峰期 30 场会议同时结束，5 分钟内要轮询 30 次妙记 API。

**原因**：妙记 AI 产物 API 限制 5 QPS。

**解决**：
- 错峰轮询（每场会议间隔 6 秒）。
- 优先处理用户主动触发的会议（更快响应）。
- 妙记 AI 处理时间从 5-30 分钟延长到 5-40 分钟，但服务稳定。

### 坑 3：Automation 规则被误关

**现象**：上线第 3 周，某员工误关了"任务状态变更 → Webhook"的 Automation。

**原因**：员工培训不到位，不知道这个 Automation 是系统关键。

**解决**：
- Automation 启用管理员权限（普通员工无法关闭）。
- 增加 Webhook 接收量监控（异常时告警）。

### 坑 4：origin 字段缺失导致无法溯源

**现象**：早期创建的任务没有 origin 字段，无法追溯到会议。

**原因**：旧版任务 API 不支持 origin。

**解决**：
- 新版任务 API 都带 origin。
- 对旧任务做批量迁移（用数据库脚本补全 origin）。

## 六、关键决策与权衡

### 决策 1：自建 vs AnyCross

**选择**：自建。

**原因**：
- 妙记 AI 产物 API **只在自建应用下可用**。
- 长期成本更低（按调用付费 vs 平台订阅）。
- 灵活性更高（可定制业务逻辑）。

### 决策 2：定时轮询 vs 事件订阅

**选择**：定时轮询为主 + Automation 桥接 + 定时补偿。

**原因**：
- 多维表格事件**不能直接订阅给外部 Bot**。
- 三层混合保证最终一致性 + 实时性。

### 决策 3：批量处理 vs 实时处理

**选择**：实时处理 + 批量补偿。

**原因**：
- 用户期望"会议结束立即有任务"。
- 批量补偿保证不丢任务。

### 决策 4：数据存储

**选择**：飞书多维表格为主 + Redis 缓存 + S3 备份。

**原因**：
- 飞书多维表格已经够用，避免引入额外数据库。
- Redis 缓存去重 + 节流。
- S3 备份妙记 AI 产物（应对飞书数据丢失）。

## 七、ROI 计算

### 投入

- **开发成本**：约 2 个工程师 × 8 周 = 640 工时。
- **服务器成本**：约 $200/月。
- **API 调用成本**：约 $50/月。
- **总投入**：约 640 工时 + $250/月。

### 产出

- **时间节省**：约 64 工时/月 × $50/小时 = $3,200/月。
- **业务收益**：项目延期减少 +18pp、销售跟进 +18pp、客户响应 -3.5 小时（难以精确量化，估算 $1,000/月）。
- **总产出**：约 $4,200/月。

### 投资回报

- **月度 ROI**：（$4,200 - $250） / $250 = 1,580%。
- **回本周期**：约 2 个月。
- **长期 ROI**：远超一次性开发成本。

---

## 八、可复用经验

### 1. 权限预留充足时间

高级权限审核需要 3-5 个工作日，**绝不能等到上线前才申请**。

### 2. 妙记 AI 准确率依赖会议质量

AI 提取的准确率与会议质量强相关。**培训会议主持人**比优化 AI 更有效。

### 3. 三层混合架构是飞书场景最优解

没有"银弹"，必须 API + Automation + 定时补偿三层协同。

### 4. 可观测性是 7×24 运行的前提

妙记 AI 处理时间不确定、Automation 可能失败、Webhook 可能丢失——**必须有监控 + 告警 + 定时补偿**。

### 5. origin 字段是闭环的关键

没有 origin，任务无法追溯。**从第一天起，所有任务都带 origin**。

## 九、本章关键 takeaway

- 飞书会议 Agent 在 50 人创业公司落地 6 个月，**任务落地率 50% → 92%**。
- 每月节省 64 工时（约 0.8 FTE），ROI 1,580%。
- 三层混合架构（API + Automation + 定时补偿）是飞书场景最优解。
- 关键挑战：妙记准确率、API 限流、Automation 误关、origin 溯源。
- 核心经验：权限预留时间、培训会议主持人、可观测性、origin 字段、三层架构。
